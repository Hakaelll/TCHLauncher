# Arquitectura

## Diagnóstico interno

`app_log.rs` escribe eventos definidos del launcher en `application-logs/launcher.jsonl`, con fecha, nivel, versión y UUID opcional validado. No admite mensajes arbitrarios: la consola de Minecraft, comandos, jugadores y credenciales permanecen fuera de estos registros. Los estados reales de proceso, inicio/cierre del launcher y fallos de mantenimiento del router alimentan el registro. Se conservan el archivo actual y uno anterior, con rotación antes de superar 2 MB. Ajustes abre la carpeta mediante un comando nativo Windows/Linux. Dos pruebas locales verifican formato, niveles, validación y rotación; apertura nativa pendiente de revisión. Esta función todavía no está en el instalador 0.12.0.

`src/` contiene la interfaz React y un cliente tipado de comandos Tauri. `src-tauri/src/` contiene módulos de almacenamiento, instalación, procesos, propiedades, jugadores y copias. Los comandos del backend validan y leen de disco; el frontend no decide por sí mismo si un servidor ha arrancado.

El registro de servidores y copias está en SQLite (`database/tchlauncher.sqlite`). Cada servidor tiene UUID y directorio propio bajo `servers/<uuid>`. Java gestionado está en `runtimes/` y las copias en `backups/<uuid>/`. El objetivo de espacio se guarda por servidor y se migra con un valor predeterminado de 20 GB para registros anteriores. Mide la carpeta del servidor, sin incluir las copias. `server.properties`, `eula.txt`, mundos y logs siguen siendo archivos ordinarios.

Las imágenes se decodifican con límites de tamaño y memoria, se recortan a 64 × 64 y se publican como PNG en `server-icon.png` dentro del servidor. Launcher y Minecraft comparten el mismo archivo. Los archivos antiguos `server-images/<uuid>` se migran antes del inicio; no se modifica la imagen original del usuario. Las operaciones requieren el servidor detenido.

`skin.rs` obtiene perfiles por UUID desde Mojang, valida que la textura procede de `textures.minecraft.net` y recorta rostro y sombrero a una cabeza de 8 × 8. Cachea PNG durante 24 horas y limita respuestas y decodificación. Un fallo conserva una caché previa o una inicial; no inventa skins. Las consultas se ejecutan fuera del hilo de interfaz.

La migración SQLite 2 añade `pinned`, con valor falso para registros anteriores. La lista ordena los fijados primero y persiste la elección.

La instalación consulta el catálogo oficial de Mojang y la API de PaperMC. La versión de Java procede de los metadatos de Minecraft. El runtime se descarga desde Eclipse Temurin, buscando JRE y después JDK de la misma versión mayor (incluido Java 16 para Minecraft 1.17.1), se verifica mediante SHA-256 y se extrae en un directorio temporal antes de moverlo a su destino. El jar Vanilla se verifica con SHA-1; Paper utiliza SHA-256 cuando la respuesta del servicio lo proporciona. No se acepta EULA automáticamente.

`ProcessManager` mantiene los procesos activos y emite eventos Tauri de estado y consola. Conserva el último estado terminal durante la sesión para que un fallo siga visible después de retirar el proceso. Envía `stop` por stdin durante inicio o ejecución y fuerza la terminación solo tras 30 segundos; las peticiones repetidas de parada se ignoran. La salida de inicio solo puede promover un proceso que aún esté en `starting`. Si se cierra la ventana con servidores activos, el usuario puede cancelarlo, detenerlos o mantener la aplicación en la bandeja del sistema. Al iniciar la aplicación, el estado se reconstruye a partir de los procesos bajo control de esta instancia; no se recuperan procesos externos u huérfanos.

`get_metrics` toma muestras del proceso Java con `sysinfo` en una tarea bloqueante separada: RAM física del proceso, CPU normalizada sobre los núcleos del equipo y contadores acumulados de lectura/escritura. Cada respuesta incluye servidor, PID y hora de muestreo; la primera lectura de CPU puede no estar disponible. El tamaño de la carpeta se cachea durante 60 segundos. La interfaz consulta aproximadamente cada tres segundos sin solapar consultas y conserva un historial de dos minutos por servidor en `App`. `telemetry.ts` descarta respuestas tardías, reinicia el historial cuando cambia el proceso, calcula tasas con el tiempo real entre muestras y separa huecos mayores de 15 segundos. El historial no se guarda en disco y no mide TPS.

Las propiedades se releen al cambiar el estado del servidor, porque Minecraft puede generar valores durante el primer inicio. Las respuestas antiguas se descartan y las modificaciones pendientes del usuario tienen prioridad hasta guardar. `Modal.tsx` presenta los diálogos mediante un portal y la capa superior nativa, con foco inicial, cierre por Escape cuando procede y restauración del foco sin desplazar el contenido.

`log.rs` añade una marca UTC a cada línea capturada, clasifica el nivel y algunos eventos operativos, y lee un tramo reciente para la Consola y el Resumen. Acepta líneas antiguas sin marca. La exportación copia el log completo a una ruta elegida por el usuario sin modificar el original. Limpiar la vista de Consola es un filtro local y conserva el historial y los eventos del Resumen.

La sección Jugadores lee los archivos Vanilla que Minecraft mantiene para jugadores conocidos, lista blanca, operadores y bloqueos. Las modificaciones con el servidor en marcha se envían por la consola, y los conectados se derivan de los eventos de entrada y salida del proceso gestionado. Tras reiniciar la aplicación, la lista de conectados se reconstruye a partir de nuevos eventos.

Las copias se hacen con el servidor detenido y se activan por intercambio de directorios. La restauración crea antes una copia del estado actual.

La importación inspecciona una carpeta existente mediante un selector nativo. Puede registrarla en su ubicación original o copiarla a la biblioteca. El `.jar` importado permanece intacto; se prepara únicamente el runtime Java compatible.

`world.rs` identifica carpetas de mundo inmediatas mediante `level.dat` comprimido y datos NBT básicos. Puede importar, duplicar y exportar a través de copias preparadas en directorios temporales y renombradas al finalizar. Rechaza nombres de ruta inseguros y enlaces simbólicos. Cambiar el mundo principal actualiza `level-name` después de guardar una copia; borrar también crea antes una copia y nunca permite eliminar el mundo activo. La creación de un servidor puede importar un mundo elegido a `world` antes de instalarlo. Las operaciones de archivos reservan el servidor y bloquean su inicio hasta terminar.

`network.rs` lee el puerto y la IP de escucha desde `server.properties`, obtiene la dirección IPv4 de la ruta local sin enviar paquetes y comprueba el puerto TCP local. El Resumen presenta la dirección LAN cuando puede determinarse. La consulta de IP pública se realiza solo si el usuario la solicita; utiliza el servicio gratuito [ipify](https://www.ipify.org/) y no comprueba la accesibilidad desde internet.

`upnp.rs` detecta IGD IPv4 mediante SSDP y limita el control HTTP al router privado anunciante, sin redirecciones ni proxy. La apertura TCP requiere confirmación explícita y coincidencia de IP/puerto con lo mostrado; su intención se persiste antes de modificar el router. Las concesiones de una hora se comprueban y renuevan solo con propietario, dirección y servidor en ejecución coincidentes. La parada, cambio de dirección/puerto y cierre activan retirada y reintento durables, conservando los registros tras eliminar un servidor. El cierre espera la limpieza en un hilo de trabajo; las concesiones temporales siguen teniendo caducidad si el router no responde. La interfaz distingue confirmación del router de accesibilidad real desde internet. Diez pruebas locales cubren transporte y ciclo de concesión; verificación con router físico y comprobación remota siguen pendientes; NAT-PMP se describe abajo.

## Limitaciones actuales

La base todavía no gestiona mapeo automático de puertos ni el resto de plataformas y gestores especificados. Se detallan en `NEXT_TODOS.md`.

## Descargas y runtime

`download.rs` usa HTTP asíncrono desde un worker, con cancelación durante conexiones, cuerpos y esperas de reintento. Hay hasta tres intentos para fallos transitorios; errores permanentes y discrepancias de hash no se reintentan automáticamente. Los bytes se escriben en archivos parciales únicos y solo se publican después de verificar el hash. Los parciales se limpian al cancelar o fallar; los artefactos ya verificados se pueden conservar.

Cada evento lleva servidor, tarea, tipo de operación, fase, bytes, total, velocidad y número de intento. El frontend conserva el estado por servidor al navegar. El servidor permanece reservado hasta terminar la tarea. La extracción comprueba cancelación entre entradas y usa un directorio de preparación. Los runtimes compartidos tienen un bloqueo por ruta; reinstalar crea una generación nueva para no sustituir ejecutables usados por otro servidor.

`runtime.rs` verifica `java -version` en un proceso oculto con tiempo límite. Configuración muestra la versión y ruta leídas, con acciones de instalar, reinstalar y verificar. En Windows se desactivan autofill y guardado de contraseñas de WebView2 sobre su hilo UI.

## Fabric

`fabric.rs` consulta el catálogo oficial, selecciona un loader estable compatible y descarga cada biblioteca desde Maven Fabric con SHA-256. Los checksums ausentes en el perfil se consultan en sus archivos oficiales `.sha256`, con tamaño acotado. El servidor Mojang conserva su comprobación SHA-1.

La instalación se prepara bajo `.tch-fabric/.stage-<uuid>` dentro del servidor y se publica como una generación completa. Solo después se actualiza SQLite; un fallo o cancelación limpia la generación sin modificar mundos ni propiedades. El manifiesto del launcher se genera con classpath relativo, líneas plegadas y clase principal leída del loader verificado. `installation.json` conserva versiones y bibliotecas para inspección. No se ejecuta un instalador externo ni se acepta la EULA.

El arranque añade `fabric.gameJarPath` para localizar el JAR Mojang de esa generación y conserva el directorio del servidor como raíz de mundos, mods, propiedades y logs. Las carpetas Fabric convencionales importadas mantienen su launcher y configuración; las generaciones de TCHLauncher también se reconocen y se copian con rutas relativas. El catálogo del asistente descarta respuestas obsoletas al cambiar de plataforma. Las actualizaciones de loader y el gestor de mods están conectados; sus límites actuales y verificaciones se documentan en las secciones siguientes y NEXT_TODOS.md.

## Custom runtime validation (0.6.3)

Each server can select a canonical Java executable through a native picker. Selection inspects `java -version`, checks the exact Java major from official Minecraft metadata and returns a preview. Confirmation repeats verification before persisting the path. Start/restart validate the configured executable in a blocking worker under the server operation reservation. Requirements are cached per Minecraft version; legacy records with no cache remain version-verified without claiming compatibility or forcing network access at launch. Managed installation refreshes the requirement cache.

## JVM and artwork (0.6.4)

JVM profiles live in a separate SQLite table linked to servers with cascading deletion. The same native argument builder supplies preview and launch, including Fabric paths. Custom saves verify the installed Java in a blocking worker under a stopped-server reservation. Artwork publication stages the original and a derived Minecraft icon, backs up previous files and rolls back the pair on failure. Full covers are loaded lazily, refreshed through a server-artwork-changed event and omitted from recurring server-list IPC payloads.

## Reviewed upgrades and experimental catalogs

`loader_identity.rs` detects identifiable Fabric/NeoForge engines from owned metadata or conventional local launcher files. `loader_update.rs` prepares a separate engine generation and commits its launch path through recovery journals and SQLite markers. Java paths are normalized only when passed to Java; filesystem ownership checks retain canonical native paths.

`minecraft_update.rs` reviews official release chronology, Java requirements, exact engine availability and installed content hashes. Managed roots are resolved as a single target-compatible dependency graph through `content.rs`; `content_storage.rs` installs that reviewed plan into a copied instance. `instance_publication.rs` switches adjacent directories and records Minecraft, launcher and Java selection together. Its recovery journal distinguishes committed from uncommitted publication; a prior safety backup remains available. Unknown/manual/modified content is preserved with warnings rather than declared compatible.

The update interface can request the existing native start command after publication. `startupVerification.ts` observes native state for up to three minutes; Java process creation does not imply readiness. Leaving the panel cancels observation without stopping Java. A failed start does not automatically restore worlds. Client gameplay/world conversion and native observation-flow validation remain pending.

Experimental selection is an explicit creation-wizard option, disabled by default. `install.rs` classifies Mojang IDs by their real release/snapshot type and intersects Fabric IDs with the official game catalog. The stable update review continues to reject experimental targets. Paper/NeoForge experimental catalog requests return a readable error. Every installation still resolves official metadata, checks published artifact hashes and verifies the exact Java major.

`log.rs` recognizes readiness only from a complete INFO startup message emitted on the native server thread, including a finite non-negative loading duration. Generic completion text, worker messages, chat and truncated lines do not establish readiness.
# Background task snapshots

DownloadTask retains its latest native Progress behind a shared mutex, including scoped modpack transfers. The engine exposes snapshots only for its registered current jobs. Frontend events remain immediate; a non-overlapping three-second reconciliation recovers missing progress and removes vanished active jobs without fabricating success. A revision check prevents a response from overwriting events received during its request. Session outcomes remain dismissible by exact server/task identity.

Manual and scheduled backups and restores reuse this task registry without changing the native process state. The tracked copy scans actual byte totals, copies in bounded chunks, syncs files and preserves permissions before publication. Cancellation and the publication boundary share the snapshot mutex: a prior cancellation prevents publication, while the publication phase rejects cancellation. Final metadata/SQLite publication and retention have no invented percentage. A restore measures its safety copy and restoration separately; cancellation before restoration publication retains the current server and completed safety copy. The native operation reservation remains held through task finish and registry cleanup.

`file_tasks` shares backup registration across manual and scheduled execution, refuses an occupied registry entry, catches worker failures and removes only the matching task identity. Scheduled stop/resume remains owned by the scheduler. Safety copies before Minecraft, loader and managed-content updates emit measured progress under their existing parent task and also protect publication from cancellation. Native scheduled Java stop/resume review, native import and content-removal interaction review remain pending. Content removal now measures the whole-server safety copy and prepared content tree separately through the same registry. Cancellation before the content switch preserves the current files and any completed safety copy; publication rejects cancellation. The confirmation dialog exposes the task and cancel action. Server imports register their future server ID as a task before copying, measure copied bytes and validate the staged launcher before publishing the directory and database entry. Cancellation before publication removes staged files; a rejected database insert removes the prepared managed directory. Registering an external folder reports its stages without fabricated copy progress. New-server operation reservations remain in the worker through terminal reporting and registry cleanup. World imports now use the same registry and measured copy path, validate the staged level.dat before publication, reject cancellation during publication and remove failed/cancelled staging directories while preserving the source. Their operation reservation remains held through terminal reporting and registry cleanup.

## Application preferences

`ApplicationSettings` organizes existing controls into seven horizontal categories without adding another sidebar. General owns appearance and startup preferences; Java, Network, Backups and scheduled tasks explicitly scope controls to the selected server. Storage exposes actual native locations and approved folder-opening actions. Advanced includes bounded launcher diagnostics and shortcuts. About uses the native binary version, OS/architecture and library EULA record. `application.rs` resolves only supported application locations or a stored server directory and rejects traversal keys, files and unsafe managed paths. Native visual/keyboard/folder-opening verification remains pending; the storage location is displayed and opened, not migrated by this interface.

## Tracked world copies

World duplication and export also use the shared task registry. They copy in measured chunks, validate the staged level.dat and share the exclusive cancellation/publication boundary before the final rename. Existing targets are rejected, original files stay intact and invalid/cancelled staging copies are removed. The stopped-server reservation stays in the worker through terminal reporting and registry cleanup. Export destination selection is a native user action; cancellation of that picker does not create a task. The frontend routes both operation kinds to Worlds and does not treat them as installation retries.

Primary-world changes and deletion use registered file tasks as well. The safety copy is measured and published first, then the task returns to preparation and checks cancellation before touching world files or properties. Completed backups remain available on cancellation or mutation failure. The target is revalidated after the copy, active-world deletion is rejected again and a second exclusive publication boundary protects the mutation. Selecting the existing principal is a no-op without a copy. The UI refreshes available backups even when these operations fail or are cancelled. Five local world tests cover the lifecycle and copy/commit boundaries; native interaction review remains pending.

## Paper tick readings

Each Paper process owns a fresh `ticks::Collector`. Explicit `request_tps` requires Running and sends `spigot:tps` over that process stdin. Pending queries expire after ten seconds; requests are limited to one per fifteen seconds. Only recognized complete native INFO stdout responses can populate three numeric averages; chat, worker, plugin-prefixed and malformed messages are rejected. Readings expire after sixty seconds and disappear when the process stops. Metrics expose an optional reading and pending state without scanning historical logs or converting CPU into TPS. Performance displays the three averages with their receipt time and handles unsupported engines/missing responses explicitly. Parser and freshness tests pass; real Paper dispatch/response, native review and other engine TPS sources remain pending. The command format follows the [Paper implementation](https://github.com/PaperMC/Paper/blob/main/paper-server/src/main/java/org/spigotmc/TicksPerSecondCommand.java) and [official command reference](https://docs.papermc.io/paper/reference/commands/).

## Storage measurements

`storage_usage.rs` measures logical file bytes in disjoint server categories and separately measures backup/preparation files. Recognized worlds use validated world metadata; symlinks are excluded and counted. Read failures return an error rather than a successful partial total. Native disk information supplies available/total bytes when a matching volume exists. SQLite stores a per-server warning percentage with cascading deletion, range validation and a default of 90. Storage settings expose a dated manual snapshot, numeric/slider threshold controls and save feedback; overview metrics read the same persisted threshold. No filesystem quota or automatic deletion is performed. Two local tests cover category totals, persisted validation, cascading deletion and invalid backup locations. Native interaction review remains pending; included in the 0.15.0 preview.

## Temporary NAT-PMP router access

`natpmp.rs` implements bounded connected-UDP exchanges with the selected private IPv4 gateway on port 5351. Address and TCP mapping replies validate version/opcode, exact packet size, result codes, the requested internal port and temporary leases; assigned external ports are retained as reported. Specific deletion uses lifetime/external port zero and forbids internal port zero, avoiding the protocol's all-mappings deletion. Two local tests cover wire parsing/errors and an actual loopback UDP address/open/close exchange. The native manager now persists intents before sending mapping requests, retains assigned external ports, renews confirmed leases halfway to expiry and attempts scoped cleanup after stop, configuration changes or application exit. Failed cleanup stays registered for retry; gateway detection uses the selected interface on Windows and the default route on Linux, with manual IPv4 fallback. Native commands and Connection controls require confirmation and prevent simultaneous UPnP/NAT-PMP registration for a server. A local manager regression verifies renewal, duplicate protection, lost replies, cleanup retry, expiry and stop during creation. Physical-router support, native interaction and remote reachability remain unverified. The protocol follows [RFC 6886](https://www.rfc-editor.org/rfc/rfc6886.html).

## Tunnel integration status

`tunnel.rs` exports `TunnelProvider` and a manager for optional TCP integrations. Provider registration may be empty and is independent of LAN/UPnP. Requests require explicit confirmation, a valid server UUID and a local TCP endpoint. Provider lease handles are excluded from serialized status. A stopped server during creation queues owned lease cleanup; failed cleanup retains an Attention session for retry, and overlapping cleanup prevents replacement until it finishes. Providers must use bounded worker-thread operations and clean any resources before returning a connection error. The former Bore integration is removed from production in 0.18.0; the contract is retained only in tests. Five local contract/lifecycle tests cover ownership, confirmation, target changes, worker disconnection and cleanup. An explicit public-relay integration test passed with a temporary echo listener; Minecraft gameplay and native interaction remain manual checks.

## Removed Bore integration

At the user's request, 0.18.0 removes the Bore panel, API bindings, native commands, production provider registration and maintenance/shutdown references. `bore.rs` and `tunnel.rs` are compiled only under `cfg(test)` to retain existing protocol/ownership regressions; they are not usable by the shipped launcher. Internet access uses UPnP/NAT-PMP or manual forwarding. No external tunnel replaces Bore.

## Process crash diagnostics

Each ProcessControl keeps at most 64 non-player output lines, capped at 2048 characters per line, and a fresh session UUID. Exit observation waits up to two seconds for stdout/stderr pumps, preserving an explicit incomplete-output flag when they remain open. `crash_diagnostics.rs` writes an atomic last-exit report before terminal publication; the read command requires the current crashed process session token and never substitutes an old report. Six deterministic rule groups identify explicit Java version, heap/native-memory, bind, mod-loader and plugin-load messages. Unknown failures retain bounded last-line evidence. Recent mod/plugin JAR timestamps are separate context, capped at 32 entries from the last day, and never claimed as the cause. The Overview review provides recommendations and existing navigation actions; no settings, content or authentication are changed automatically. Symlink report folders/files and oversized records are rejected. Rule references: [Oracle UnsupportedClassVersionError](https://docs.oracle.com/en/java/javase/24/docs/api/java.base/java/lang/UnsupportedClassVersionError.html), [Oracle memory failures](https://docs.oracle.com/javase/8/docs/technotes/guides/troubleshoot/memleaks002.html), [Paper troubleshooting](https://docs.papermc.io/paper/basic-troubleshooting/). Local rules/persistence and log-tag regressions pass; An explicit integration with installed Java 21 verifies actual stderr/log capture, failure/success codes, native terminal state and fresh session reports using an unsupported class and a subsequent successful process. Minecraft/EULA/worlds are not involved. Minecraft crash behavior and desktop verification remain pending. Included in 0.15.1.

Property keys accept ASCII letters/digits, hyphens, dots and underscores; this permits Minecraft query.port and RCON keys during full-settings saves. Whitespace, delimiters and newline injection remain rejected. The full-properties regression preserves comments, account verification and query/RCON values while changing a game rule, and verifies failed validation leaves the file untouched.

NAT-PMP maintenance and shutdown now decode each durable row independently. Invalid JSON, destination mismatches and invalid stored ports produce an identified error without contacting or deleting the untrusted record. Other valid rows continue renewal/cleanup even when another transport fails. Failures are reported after the pass; recoverable cleanup remains durable for retry. Two local regressions exercise these paths using actual SQLite persistence and controlled transports; physical routers are not exercised. This change is after the 0.15.1 installer.

Crash reports now keep `last-exit.json` for the current-session check and `last-failure.json` for explicit historical review. Only unsuccessful/unknown exits replace the latter; successful sessions preserve it. The historical endpoint verifies the stored server identity independently of in-memory process state and falls back to the former single-file format when no separate failure file exists. Overview exposes a native disclosure with the stored timestamp and a clear distinction from current status. SQLite/process state and automatic crash restart are unchanged. Three local diagnostics regressions and the real Java 21 failure-then-success integration pass; the integration also verifies access with a fresh process manager, not a native desktop relaunch. This is after 0.15.1.

Scheduler and crash-restart workers own a `WorkerPermit` until result persistence/event reporting ends; its destructor releases capacity even on unwind. Action execution uses a bounded panic boundary with a fixed user-facing failure message and no arbitrary panic payload persisted. Scheduled actions finish through their durable result path, while automatic restarts use the existing delay/attempt policy. Seven scheduler regressions include a real thread panic, SQLite result persistence, capacity release and one-time no-replay behavior; native scheduled Java control remains unverified. These changes are after 0.15.1.

Scheduled claims inspect up to 100 due candidates inside the same immediate SQLite transaction. Each decoded occurrence must have valid IDs/action/date/interval and a representable next occurrence. Invalid occurrences are disabled with a readable result and preserved values; processing continues to the next valid task. Recurrence uses checked arithmetic and skips missed ticks. Re-enabling validates the stored occurrence under an immediate transaction. Listing projects invalid rows into an explicit `invalid` display record, retaining their identifier and enabled/running flags, so malformed intervals/dates cannot crash rendering or hide other tasks. The UI offers removal without activation. Nine scheduler tests exercise zero/negative intervals, negative dates, date boundaries, removal, normal claims and thread failure; TypeScript/Vite pass. Native interaction remains pending. Changes are after 0.15.1.

Backup snapshot metadata now has an optional typed reason, preserving format-1 compatibility. New manual/scheduled and pre-change copies record their actual trigger; restore safety snapshots explicitly record before-restore. The list command reads saved metadata in a blocking worker, checks managed directory identity and rejects symlinks/oversized metadata. Each copy keeps its list entry when metadata fails, with a scoped error and no guessed version/engine/reason. The frontend groups date/reason/version in the existing list and repeats stored context in restore confirmation. Twelve backup tests cover metadata compatibility, scoped corruption, foreign-path rejection and restore preservation; TypeScript/Vite pass. Native review and automatic stop-trigger backups remain pending. Changes are after 0.15.1.

## Backup after a clean stop

`stop_backup.rs` stores an explicit off-by-default server preference, last process token, phase/date/result in SQLite. The process exit record includes successful status and whether the session reached Running. The observer only reserves inactive, stopped servers with eligible exits; the universal process start path checks a pending stop copy before starting Java, covering immediate restart/start races while the caller owns the operation reservation. Copies use the measured registry, cancellation, existing retention and a ServerStop snapshot reason. The claim precedes copying, so the same session does not replay after failure, cancellation or application recovery. Enabling ignores the currently known exit. Backups expose the preference/result without adding a modal for routine preference changes.

Stop-and-exit reserves the active servers, waits for clean terminal states and configured copies, and keeps the application open on failure. Native exit cleanup waits for already-owned file operations and handles eligible stops missed by the observer before removing router mappings. Window close during an owned file task is prevented. Two real filesystem/SQLite regressions cover opt-in, exclusions, successful copy, preserved contents, cancelled stages, insert failure, status persistence and recovery without replay. Native Minecraft readiness/stop, immediate restart and desktop shutdown interaction still need manual verification. Changes are after 0.15.1.

## Current-process startup duration

ProcessControl records a monotonic launch instant immediately before spawning Java. The existing recognized ready event records the first Running instant; repeated ready lines cannot replace it. Metrics returns PID, uptime and optional startupDurationMs from one process-map snapshot. The duration is absent until readiness and when the process has been removed, and each new process owns a fresh timestamp. Performance presents seconds with a description of the measurement boundaries. This measures observed launcher readiness, not the internal duration printed by Minecraft; native Minecraft/desktop verification remains pending.

## Existing operator settings

Grant and revoke still use Minecraft commands. An explicit stopped-server editor may change only level (0–4) and bypassesPlayerLimit for one existing UUID in ops.json. Engine reserves stopped files through the native worker. The editor validates typed entries and uniqueness, checks displayed permissions for stale edits, preserves original names/UUIDs/unknown fields and other entries, writes and syncs a temporary replacement, rechecks the original bytes, and stores a synced exact-byte ops-before-UUID.json safety copy before the shared rollback-capable replacement. Safety copies remain in the server folder; this is not a whole-server snapshot. A real-file regression covers identity/data preservation, safety bytes, stale edits, missing/duplicate UUIDs, invalid level and malformed JSON. Effects after Java startup and native visual/keyboard review remain unverified. Format reference: https://docs.papermc.io/paper/reference/vanilla-data-files/

The process output pump now updates its per-session connected-name set from the same LogEvent that is emitted to the console. The shared player-message validator accepts only a complete valid Minecraft name followed by the exact join/leave suffix. Terminal colors are removed before classification, and header extraction preserves delimiters inside chat, including unsigned or unprefixed messages. Tracking also requires matching player category and event kind. Stored raw lines retain their color bytes, while recent reads reconstruct the same normalized events. A real-file append/read-back regression covers Paper and Vanilla formatting, colored names, repeated joins/leaves and chat/command/plugin impersonation. Native Minecraft connections remain unverified; no changes to UUID/authentication or stored player profiles are made by this path.

## Observed startup phases (after 0.16.0)

A per-ProcessControl phase begins at Launching, advances on normalized native world_load/spawn_prepare/startup events and never regresses. Thread/INFO or Paper/INFO headers and bounded exact messages determine those events; chat, commands and plugin-prefixed messages are excluded. Spawn percentages identify the preparation phase only, never overall progress or readiness. The metrics process snapshot includes this ephemeral phase; a new process starts fresh, and removed processes have no phase. Overview renders a compact ordered Java/World/Ready path with current/completed/pending semantics and a live description. A frontend start generation clears old metrics and rejects already outstanding replies from previous starts. Tests cover valid/invalid messages and a read-only scan of the provided actual Paper log; live Minecraft/Tauri and native visual verification remain pending.

Startup phase changes emit server-startup with a session UUID immediately on launch and only on progression. The frontend accepts a new session only from its launch event, ignores duplicates/regression and rejects updates from a different session. This keeps short starts visible without increasing metric polling. Two frontend regressions cover this event contract; initial snapshots still supply the current native phase when launch events were not observed.

## Minecraft status query and heap diagnostics (after 0.16.0)

Connection offers an explicit status query against the registered server's numeric IP/port. The native worker re-reads properties, checks process state and enable-status, and makes no login or configuration change. Java SLP framing uses bounded VarInts, a 128 KiB packet cap, typed optional advertised fields and a matching ping token. A three-second deadline covers connection and reads/writes; the ping is sent before waiting for status to support servers that defer that response. The frontend clears old results and ignores outstanding replies across server/state changes. Query latency is not external reachability or player latency. Protocol reference: https://github.com/EaseCation/mcget#protocol-details

Heap diagnostics read only performance data for a PID obtained from ProcessManager. Candidate files are bounded, regular, non-symlink files in native temporary hsperfdata directories. The parser validates the version-2 prologue, byte order, accessibility, entry counts, offsets, types, units and sums; generation capacity and space usage remain separate from resident RAM. Unsupported collectors, disabled counters, startup/inconsistent samples and unreadable files produce scoped unavailability. Collector invocation totals include the categories exported by HotSpot and are not presented as a count of full collections. No runtime flags, JMX listeners or collection requests are added. Samples reflect Java counters and do not establish retained live objects or a memory leak. See OpenJDK's perfMemory.hpp and g1MonitoringSupport.cpp in https://github.com/openjdk/jdk21u . Parser checks and a private 64 MiB Java 21 workload pass; the workload requires normal Windows shared-memory access, unavailable inside this execution sandbox. Client Minecraft and account authentication remain separate future work.

### Memory report history

`memory_report::History` receives only native `get_metrics` observations. It retains at most 901 samples over 30 minutes per observed server, with a 32-server bound. It records only the selected server's existing metrics polling, not an additional background sampler. ## Graceful and forced shutdown

Exit diagnostics persist a `forced` flag; old reports without it read as false. Forced zero-code exits still enter diagnostic history. Forced-close evidence precedes retained known errors and replaces the generic unknown-cause finding. Saved diagnostic attribution uses native header severity, excluding structured INFO descriptions even when their message contains a recognized error name.

Normal stop writes the server `stop` command and waits for the real process exit. It does not impose an automatic kill deadline. Restart and application-exit orchestration can time out and report the still-active process without terminating it.

The native force-stop preview is available only in `stopping` and carries the exact process session and PID. Confirmation revalidates that session and state before killing the owned child. The normal monitor reaps the process and publishes its terminal state. A forced exit is unsuccessful even if the OS reports a zero exit code; it is user-requested, so clean-stop backups and unexpected-crash retries are excluded. Restart refuses to continue after an unsuccessful exit. The UI dialog keeps cancellation focused and explains possible world-file loss.
